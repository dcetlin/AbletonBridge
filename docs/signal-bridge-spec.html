AbletonBridge

SignalBridge

M4L device that reads audio amplitude and sends it as a normalized OSC signal to an external receiver. Configurable by MCP — zero manual mapping.

The Problem

Routing audio-derived signals (onset detection, amplitude envelopes, pitch contours) from Ableton to an external system typically requires manual parameter mapping in the GUI. The LOM has no API for creating live.remote~ connections or macro mappings — that wall is structural, not a missing feature.

The fix: don't use the parameter mapping system. Audio → OSC is a straight line that M4L handles natively.

Signal Flow

Typical (5 components, 2 manual steps)

Audio on track → Envelope Follower → manual map → Rack macro → manual map → OSC plugin → Receiver

With SignalBridge (1 device, 0 manual steps)

Audio on track → SignalBridge → Receiver

SignalBridge reads audio directly from the track, envelope-follows it, and sends the result over OSC. The signal never enters Ableton's parameter domain.

Three Modes

Envelope
mode: "envelope"

Reads audio amplitude on the track. Audio signal → envelope follower → OSC.

Observer
mode: "observer"

Watches any LOM parameter via live.observer and forwards changes as OSC. For parameter-derived signals.

Passthrough
mode: "passthrough"

Accepts a value directly from MCP via lom_set on the device parameter. For MCP-computed signals.

v1 ships envelope-only. Observer and passthrough are deferred — different sources of truth that shouldn't share plumbing prematurely.

Max Patch Architecture

Envelope mode (primary path)

plugin~ → peakamp~ 1 → slide~ [attack_samps] [release_samps]
  ├→ live.meter~ (UI tap, before downsampling)
  └→ snapshot~ 16 → gate [threshold] → [smoothing] → [invert?] → clip 0. 1.
       ├→ pak /Params/[name] f → udpsend
       └→ (if rms_out) average~ → snapshot~ 16 → pak /Params/[name]Rms f → udpsend
Implementation notes: slide~ takes sample counts, not milliseconds — convert via mstosamps~ or ms * sr / 1000. snapshot~ 16 downsamples from signal rate to ~60 Hz control rate before udpsend (which is control-rate only). Tap live.meter~ before downsampling to display the smoothed audio signal natively. Smoothing stage is bypassed when set to none (receiver owns the curve); linear uses line; one-pole uses slide (control rate).

Observer mode (deferred to v2)

Different source of truth — shouldn't share plumbing with envelope mode prematurely. Split into a separate device if it earns its existence.

Passthrough mode (deferred to v2)

Same reasoning. May converge with observer or stay separate.

Shared output stage (control rate)

[input 0–1] → gate [active] → clip 0. 1. → pak /Params/[name] f → udpsend [host] [port]
Reporting: The device also sends its current value + status to the MCP server over UDP (same pattern the existing dashboard uses). This powers the dashboard signals panel.

Device Parameters

All settable via lom_set. MCP loads the device and configures it in one sequence.

ParameterTypeDefaultDescription
param_namemenu—OSC address becomes /Params/<value>. User-configurable live.menu — populate with your project's signal names. MCP sets by index via lom_set.
activetoggle1Enable / disable output
attackfloat ms5.0Envelope attack time
releasefloat ms50.0Envelope release time

smoothingmenuone-polenone · linear · one-pole — controls whether SignalBridge or the receiver owns the curve. Use none when the receiver handles its own smoothing.
gatefloat0.0Zeros output below this threshold (0–1). Onset signals use ~0.3 to avoid false triggers in silence.
inverttoggle0Outputs 1 - value. Makes inverted mappings visible in Ableton instead of hidden in receiver-side expressions.
rms_outtoggle0Sends a second OSC output at /Params/<name>Rms with RMS value. One device → two signals, saves a track. The receiver must be configured to accept the <name>Rms address — unmatched addresses are typically dropped silently.
dest_portint3333OSC destination port
Range is 0–1 by default. Out-of-range values are structurally impossible — clip 0. 1. enforces the range at the output stage before OSC packing.

AbletonBridge Integration

Workflow tool

@mcp.tool()
@_tool_handler("creating signal track")
def add_signal_track(
    ctx: Context,
    name: str,
    wav_path: str,
    param_name: str,
    param_index: int = -1,
    osc_port: int = 3333,
    osc_prefix: str = "/Params",
    attack_ms: float = 5.0,
    release_ms: float = 50.0,
    gate: float = 0.0,
    invert: bool = False,
) -> str:

What it does

  1. Create audio track named {name}_signal
  2. Load WAV from wav_path into arrangement
  3. Disable warp, reset start marker to 0 (bracket LOM paths)
  4. Load SignalBridge via load_instrument_or_effect
  5. Set device params: param_name, mode, attack, release
  6. Mute track (signal tracks shouldn't be audible)

Implemented as a compound workflow tool in MCP_Server/tools/workflows.py — orchestrates existing commands, no new Remote Script handler needed. Accepts any param_name string and configurable osc_port / osc_prefix.

OSC Output Contract

SignalBridge sends standard OSC messages. Configure the address prefix and port to match your receiver.

PropertyDefault
TransportUDP to 127.0.0.1
PortConfigurable (default 3333)
Address{osc_prefix}/{param_name} (default prefix /Params)
ValueSingle float, 0–1 normalized
One-writer guard: Some OSC receivers ignore incoming messages for parameters that are being computed internally. If a signal appears dead, check whether the receiver has claimed that parameter — the device's output may be silently dropped.

Debug flow

  1. Something wrong at the receiver → open dashboard at :9880
  2. Signals panel shows which signal is flat, missing, or out of range
  3. Look at the track in Ableton → device face shows real-time meter
  4. Tweak attack/release on the device, see results immediately

What Stays Unchanged

Existing parameter mapping chains (rack macros, VST/AU plugins) continue to work for non-audio-derived signals. SignalBridge is additive — it handles the audio-to-OSC path and doesn't interfere with other routing.

All existing MCP tools — add_signal_track composes existing primitives internally.

Review Findings

Alexander structural review

Strongest feature: The shared output stage is the right center — the device's job is "get a normalized value out over OSC," not "envelope follow." The clip 0. 1. is the boundary's physical expression.

Weakness — inner calm: Three modes in one device is premature. Envelope reads audio (MSP domain). Observer watches LOM (control domain). Passthrough takes MCP values. These are three different sources of truth sharing plumbing. If any mode grows, they'll compete for patch real estate.

Recommendation: Ship envelope-only as v1. Observer and passthrough can be added later if they converge on the same output contract, or split into separate devices if they diverge.

Note: Observer mode reintroduces a dependency on the parameter domain the device was designed to bypass — it thins the boundary.

Max/MSP feasibility

Corrections applied above:

  • slide~ takes sample counts, not ms — needs mstosamps~ conversion
  • Added snapshot~ 16 to downsample to control rate before udpsend
  • All output-stage objects are control-rate (clip not clip~, gate not gate~)
  • live.meter~ taps before downsampling to display smoothed audio natively

Example presets by signal type

Signal typeAttackReleaseGateSmoothingNotes
transient / onset≤5 ms~40 ms0.3noneSharp response. Let the receiver handle further smoothing.
amplitude envelope~10 ms~100 ms0.0one-poleSmooth tracking. SignalBridge owns the curve.
pitch / spectral~10 ms~100 ms0.0noneReceiver-side smoothing for slow signals.
gate / trigger≤5 ms~40 ms0.3noneBinary-like signal — fast edges, threshold filters noise.
Avoid duplicating receiver-side processing: If your receiver already handles curve shaping, rate limiting, or bipolar remapping, set smoothing to none and let it do the work. SignalBridge's job ends at producing a clean 0–1 value.

Resolved: string parameters → live.menu

M4L device parameters are numeric only. param_name is implemented as a live.menu with user-configurable entries — populate it with your project's signal names. MCP sets by index via lom_set. Adding a new signal = one menu entry in the Max patch.
