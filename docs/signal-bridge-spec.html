AbletonBridge

SignalBridge

M4L device that reads audio amplitude and sends it as a normalized OSC signal to an external receiver. Configurable by MCP — zero manual mapping.

The Problem

Routing audio-derived signals (onset detection, amplitude envelopes, pitch contours) from Ableton to an external system typically requires manual parameter mapping in the GUI. The LOM has no API for creating live.remote~ connections or macro mappings — that wall is structural, not a missing feature.

The fix: don't use the parameter mapping system. Audio → OSC is a straight line that M4L handles natively.

Signal Flow

Typical (5 components, 2 manual steps)

Audio on track → Envelope Follower → manual map → Rack macro → manual map → OSC plugin → Receiver

With SignalBridge (1 device, 0 manual steps)

Audio on track → SignalBridge → Receiver

SignalBridge reads audio directly from the track, envelope-follows it, and sends the result over OSC. The signal never enters Ableton's parameter domain.

Device Mode

v1 is envelope-only: reads audio amplitude from the track, envelope-follows it, sends the result over OSC. Additional modes (LOM parameter observer, MCP passthrough) are deferred to v2 — see Future.

Max Patch Architecture

Signal chain (v1 — envelope mode)

plugin~ → abs~ → slide~ [attack_samps] [release_samps]
  ├→ live.meter~ (UI tap, before downsampling)
  └→ snapshot~ 16 → expr $f1 * ($f1 >= $f2) [gate] → [invert?] → clip 0. 1.
       → prepend /Params/[name] → udpsend 127.0.0.1 [port]
Implementation notes: slide~ takes sample counts, not milliseconds — convert via mstosamps~. snapshot~ 16 downsamples from signal rate to ~60 Hz control rate before udpsend (control-rate only). live.meter~ taps before downsampling to display the smoothed audio signal natively. Gate uses multiplication (expr $f1 * ($f1 >= $f2)) so output zeros below threshold instead of holding the last value.

All settable via lom_set. MCP loads the device and configures it in one sequence.

AbletonBridge Integration

Workflow tool

add_signal_track(
    name: str,
    wav_path: str,
    param_index: int = 0,    # which live.menu slot (0–7)
    osc_port: int = 3333,
    attack_ms: float = 5.0,
    release_ms: float = 50.0,
    gate: float = 0.0,
    invert: bool = False,
)

What it does

  1. Create audio track named {name}_signal
  2. Load WAV from wav_path into arrangement at position 0
  3. Disable warp, reset start marker to 0 (bracket LOM paths)
  4. Load SignalBridge.amxd via load_instrument_or_effect — errors if device not found
  5. Set all device params via set_device_parameters_batch — batch errors surfaced as warnings
  6. Read back actual device state via get_device_parameters — returned values come from the device, not echoed inputs
  7. Mute track (signal tracks shouldn't be audible; device still receives audio)

Implemented as a compound workflow tool in MCP_Server/tools/workflows.py. Orchestrates existing commands — no new Remote Script handler needed.

OSC Output Contract

SignalBridge sends standard OSC messages to localhost.

PropertyValue
TransportUDP to 127.0.0.1 (localhost only)
PortConfigurable via Dest Port parameter (default 3333)
Address/Params/<menu entry> — determined by the Param Name live.menu selection
ValueSingle float, 0–1 normalized
One-writer guard: Some OSC receivers ignore incoming messages for parameters that are being computed internally. If a signal appears dead, check whether the receiver has claimed that parameter — the device's output may be silently dropped.

End-to-End Workflow

Adding a new signal

add_signal_track(
    name="kick",
    wav_path="/path/to/kick_envelope.wav",
    param_index=0,
    attack_ms=2.0,
    release_ms=80.0
)

One call. Track appears, WAV loads, SignalBridge configures, signal flows to the receiver. The response includes device_state read back from the actual device.

Debug flow

  1. Signal missing at the receiver → check the device face in Ableton (real-time meter shows current value)
  2. Meter shows signal but receiver doesn't get it → check OSC address (Param Name menu) and port (Dest Port) match receiver expectations
  3. If the receiver has a one-writer guard, check that it hasn't claimed the parameter
  4. Tweak attack/release on the device face, see results immediately

What Stays Unchanged

Existing parameter mapping chains (rack macros, VST/AU plugins) continue to work for non-audio-derived signals. SignalBridge is additive — it handles the audio-to-OSC path and doesn't interfere with other routing.

All existing MCP tools — add_signal_track composes existing primitives internally.

Setup

  1. Open M4L_Device/SignalBridge.maxpat in Max for Live (drag into an Ableton track, then click the wrench icon)
  2. Edit the Param Name live.menu entries to match your project's signal names
  3. File → Save As → save as SignalBridge.amxd (or File → Freeze Device, then save)
  4. Move the .amxd to your User Library: ~/Music/Ableton/User Library/Presets/Audio Effects/Max Audio Effect/
  5. The MCP tool resolves SignalBridge.amxd from Ableton's browser. If the device isn't found, the tool errors with setup instructions.
The .maxpat is the source file. Ableton cannot load it directly — it must be saved/frozen as .amxd first. The repo ships the .maxpat because .amxd is a binary format that requires the Max editor to produce.

Acceptance Criteria

SignalBridge.amxd loads via load_instrument_or_effect
All 7 device parameters settable via lom_set
Audio in → normalized 0–1 float → OSC output on configured port
add_signal_track creates a complete signal track in one call
Device load failure is an error, not silent
Device state read back after configuration — returned values come from the device
Range enforced by clip 0. 1. — out-of-range values structurally impossible
All AbletonBridge tests pass (381 including structural maxpat tests)

Future

Deferred from v1. These features may be added if they earn their place.

  • Observer mode: Watch any LOM parameter via live.observer and forward changes as OSC. Different source of truth than audio — may warrant a separate device.
  • Passthrough mode: Accept values directly from MCP via lom_set. May converge with observer or stay separate.
  • Smoothing menu: none / linear / one-pole toggle to control whether SignalBridge or the receiver owns the smoothing curve.
  • RMS dual output: Send both peak and RMS values from one device (/Params/<name> + /Params/<name>Rms).
  • Dashboard signals panel: Live-updating table of all active SignalBridge instances on the :9880 dashboard, powered by UDP status reports from the devices.
  • Configurable dest host: Currently localhost only. Remote OSC targets would need a host parameter.
  • Dynamic param name via OSC config channel: Accept string names over OSC instead of a fixed menu, for fully dynamic signal routing.
