Soulrise / AbletonBridge

SignalBridge

M4L device that reads audio amplitude and sends it as a normalized OSC signal to TouchDesigner. Configurable by MCP — zero manual mapping.

The Problem

Adding a new audio-derived signal (onset, articulation, pitch contour) from Ableton to TouchDesigner currently requires three manual mapping steps in the GUI. The LOM has no API for creating live.remote~ connections or macro mappings — that wall is structural, not a missing feature.

The fix: don't use the parameter mapping system. Audio → OSC is a straight line that M4L handles natively.

Signal Flow

Current (5 components, 2 manual steps)

WAV on track → Envelope Follower → manual map → NATIVIZE macro → manual map → Nativize 256 → TD :3333

Proposed (1 device, 0 manual steps)

WAV on track → SignalBridge → TD :3333

SignalBridge reads audio directly from the track, envelope-follows it, and sends the result over OSC. The signal never enters Ableton's parameter domain.

Three Modes

Envelope
mode: "envelope"

Reads audio amplitude on the track. The Soulrise default — WAV signal → envelope follower → OSC.

Observer
mode: "observer"

Watches any LOM parameter via live.observer and forwards changes as OSC. For parameter-derived signals without Nativize.

Passthrough
mode: "passthrough"

Accepts a value directly from MCP via lom_set on the device parameter. For MCP-computed signals.

v1 ships envelope-only. Observer and passthrough are deferred — different sources of truth that shouldn't share plumbing prematurely.

Max Patch Architecture

Envelope mode (primary path)

plugin~ → peakamp~ 1 → slide~ [attack_samps] [release_samps]
  ├→ live.meter~ (UI tap, before downsampling)
  └→ snapshot~ 16 → gate [threshold] → [smoothing] → [invert?] → clip 0. 1.
       ├→ pak /Params/[name] f → udpsend
       └→ (if rms_out) average~ → snapshot~ 16 → pak /Params/[name]Rms f → udpsend
Implementation notes: slide~ takes sample counts, not milliseconds — convert via mstosamps~ or ms * sr / 1000. snapshot~ 16 downsamples from signal rate to ~60 Hz control rate before udpsend (which is control-rate only). Tap live.meter~ before downsampling to display the smoothed audio signal natively. Smoothing stage is bypassed when set to none (TD owns the curve); linear uses line; one-pole uses slide (control rate).

Observer mode (deferred to v2)

Different source of truth — shouldn't share plumbing with envelope mode prematurely. Split into a separate device if it earns its existence.

Passthrough mode (deferred to v2)

Same reasoning. May converge with observer or stay separate.

Shared output stage (control rate)

[input 0–1] → gate [active] → clip 0. 1. → pak /Params/[name] f → udpsend [host] [port]
Reporting: The device also sends its current value + status to the MCP server over UDP (same pattern the existing dashboard uses). This powers the dashboard signals panel.

AbletonBridge Integration

New handler

@command("add_signal_track", modifying=True)
def add_signal_track(
    song,
    name: str,
    wav_path: str,
    *,
    param_name: str,
    mode: str = "envelope",
    attack_ms: float = 5.0,
    release_ms: float = 50.0,
    ctrl: 'ControlSurface | None' = None,
) -> dict:

What it does

  1. Create audio track named {name}_signal
  2. Load WAV from wav_path into arrangement
  3. Disable warp, reset start marker to 0 (bracket LOM paths)
  4. Load SignalBridge via load_instrument_or_effect
  5. Set device params: param_name, mode, attack, release
  6. Mute track (signal tracks shouldn't be audible)

MCP tool

@mcp.tool()
@_tool_handler
async def add_signal_track(
    name: str,
    wav_path: str,
    param_name: str,
    mode: str = "envelope",
    attack_ms: float = 5.0,
    release_ms: float = 50.0,
) -> str:
    """Create a signal track with SignalBridge routing audio to TD via OSC."""
    return await send_command("add_signal_track", {
        "name": name, "wav_path": wav_path, "param_name": param_name,
        "mode": mode, "attack_ms": attack_ms, "release_ms": release_ms,
    })

TD Contract

No TD changes needed. SignalBridge speaks the same protocol TD already listens on.

PropertyValue
TargetUDP 127.0.0.1:3333
Address/Params/<Name> — case-sensitive, must match Params custom par label exactly
ValueSingle float, 0–1 normalized
UnmatchedSilently dropped by TD
Reserved/nativize/time — don't reuse
One-writer guard: TD's OSCManager ignores incoming OSC for params that are in non-CONSTANT mode (TD-computed) or are active SignalMapper route targets. If a signal appears dead, check whether TD has a route claiming that param — the device's output is silently dropped until the route is removed.
Param ordering: New params must be appended to the TD Params surface, never inserted. Inserting shifts Nativize indices and breaks existing macro mappings.

End-to-End Workflow

Adding a new visual signal

add_signal_track(
    name="onset",
    wav_path="/path/to/onset_signal.wav",
    param_name="Onset"
)

One call. Track appears, WAV loads, SignalBridge configures, signal flows to TD.

Debug flow

  1. Something wrong in TD → open dashboard at :9880
  2. Signals panel shows which signal is flat, missing, or out of range
  3. Look at the track in Ableton → device face shows real-time meter
  4. Tweak attack/release on the device, see results immediately

What Stays Unchanged

Nativize 256 keeps handling song position (/nativize/time) and any manually-mapped non-signal parameters. SignalBridge routes around it for audio-derived signals.

NATIVIZE rack stays for performance macros and anything that isn't an audio-derived signal.

All existing MCP tools — add_signal_track composes existing primitives internally.

Review Findings

Alexander structural review

Strongest feature: The shared output stage is the right center — the device's job is "get a value to TD cleanly," not "envelope follow." The clip 0. 1. is the boundary's physical expression.

Weakness — inner calm: Three modes in one device is premature. Envelope reads audio (MSP domain). Observer watches LOM (control domain). Passthrough takes MCP values. These are three different sources of truth sharing plumbing. If any mode grows, they'll compete for patch real estate.

Recommendation: Ship envelope-only as v1. Observer and passthrough can be added later if they converge on the same output contract, or split into separate devices if they diverge.

Note: Observer mode reintroduces a dependency on the parameter domain the device was designed to bypass — it thins the boundary.

Max/MSP feasibility

Corrections applied above:

  • slide~ takes sample counts, not ms — needs mstosamps~ conversion
  • Added snapshot~ 16 to downsample to control rate before udpsend
  • All output-stage objects are control-rate (clip not clip~, gate not gate~)
  • live.meter~ taps before downsampling to display smoothed audio natively

What TD already handles (don't duplicate): Rate limiting (cook rate + AutoOSC filter), curve shaping (SignalMapper's per-route Curve param), bipolar center mapping. SignalBridge's job ends at producing a clean 0–1 value.

Resolved: string parameters → live.menu

M4L device parameters are numeric only. param_name is implemented as a live.menu with the 12 known Soulrise signal labels. MCP sets by index via lom_set. Adding a new signal = one menu entry in the Max patch. Bilatlive and Bilatsynth are excluded (TD-computed — would be dropped by the one-writer guard).
